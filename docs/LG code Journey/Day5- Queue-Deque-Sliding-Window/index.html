Day5 - Queue & Deque & Sliding window Max

Date: 16/04/2026 Topic: Queue, Deque & Sliding Window Maximum — Maintaining a Decreasing Deque. Comparing Priority Queue vs Deque. Total Problems Solved: 4

I. THEORY​

🔁 QUEUE​

1. Definition​

A Queue is a data structure that follows the FIFO principle: First In, First Out — like a real-world line.

2. Core Idea​

  • Add elements to the back (enqueue)
  • Remove elements from the front (dequeue)

No random access like an array.

3. When to Use​

Indicators:

  • "process in order"
  • "spread layer by layer" (BFS)
  • "task queue"

Use cases:

  • BFS (on graphs/trees)
  • Simulation (queue-based systems)
  • Processing tasks in arrival order

4. Complexity​

TypeComplexity
Time (per operation)O(1)
SpaceO(n)

5. Common Pitfalls​

  • Using list.pop(0) → O(n) per operation; use deque instead
  • Not checking if queue is empty before dequeuing
  • Confusing with Stack (LIFO)

🔀 DEQUE (Double-Ended Queue)​

1. Definition​

A Deque is a double-ended queue — elements can be added or removed from both ends.

2. Core Idea​

Four operations:

  • push_front / push_back
  • pop_front / pop_back

Much more flexible than a regular queue.

3. When to Use​

Indicators:

  • "sliding window"
  • "maintain continuous max/min"
  • Need to operate on both ends

Use cases:

  • Sliding Window
  • Monotonic Queue

4. Complexity​

TypeComplexity
Time (per operation)O(1)
SpaceO(n)

5. Common Pitfalls​

  • Using a plain list instead of deque → slower
  • Getting push/pop order wrong → incorrect logic
  • Forgetting to remove elements that fall outside the window

🏆 SLIDING WINDOW MAXIMUM (Critical)​

1. Definition​

Given an array and a window of size k — as the window slides, find the maximum value in each window position.

2. Core Idea​

Use a Monotonic Deque (decreasing):

  • Deque stores indices
  • Always maintains:
arr[deque[0]] >= arr[deque[1]] >= ...

How it works:

  1. Remove elements from the back that are smaller than the new element
  2. Append the new index
  3. Remove elements from the front that are outside the window
  4. Front of deque is always the current maximum

Essence: Eliminate all elements that have "no chance of becoming the max in the future"

3. When to Use​

Golden indicators:

  • "max/min of subarray of size k"
  • "sliding window"
  • "optimize from O(n·k) to O(n)"

Examples: LeetCode 239, max/min in a window, stock/temperature/log data

4. Complexity​

TypeComplexity
TimeO(n)
SpaceO(k)

5. Common Pitfalls​

  • Storing values instead of indices → can't control window boundaries
  • Forgetting to remove out-of-window elements from the front
  • Not maintaining the deque's monotonic property
  • Logic confusion:
    • Max → decreasing deque
    • Min → increasing deque

II. PROBLEMS​

Problem 1: Printer Queue — Programmers​

1. Problem Summary​

There is a queue of documents to print. Each document has a priority.

Printing rules:

  1. Take the document at the front of the queue
  2. If any document in the queue has a higher priority → move current document to the back
  3. Otherwise → print it

Goal: Given a target location, find the order in which that document is printed.

2. Approach​

Why this solution:

  • Process in order + rotation → natural Queue + Simulation
  • Elements can be "pushed to the back"

Patterns applied:

  • Queue / Simulation
  • Greedy (always print the highest priority first)

Theory connection:

  • Queue: pop from front, push to back
  • Greedy: always prioritize the element with the highest priority
  • Can use: Queue + max() or Priority Queue (Heap)

3. Solution Idea​

Approach: Queue + max()

Step 1: Create queue storing (index, priority)

Step 2: Loop:
  - Take the front element (cur)
  - If any element in queue has higher priority:
      → move cur to the back
  - Otherwise:
      → print (count++)
      → if cur.index == location → return count

💡 Insight: No need to sort everything — just check "is there anyone with higher priority?"

4. Code​

from collections import deque

def solution(priorities, location):
    queue = deque([(i, p) for i, p in enumerate(priorities)])
    count = 0

    while queue:
        cur = queue.popleft()

        # if any element has higher priority
        if any(cur[1] < q[1] for q in queue):
            queue.append(cur)
        else:
            count += 1
            if cur[0] == location:
                return count

5. Complexity​

TypeComplexity
TimeO(n)
SpaceO(n)

6. Key Learnings​

1. Recognizing advanced Queue problems

Not pure FIFO — has a "conditional rotation" behavior

2. Key insight

Queue + condition → Simulation

3. Common mistakes

  • Sorting first → wrong order
  • Not storing index → lose track of target position
  • Misunderstanding logic (printing immediately)

4. Two approaches compared:

ApproachIdea
Queue + max()Easy to understand
Max HeapMore optimal

5. DSA Mapping:

ComponentMeaning
QueuePrint queue
RotatePush to back
Max checkPriority enforcement

6. Level-up:

Queue is not just FIFO — it can "transform" with conditional logic.

Problem 2: Trucks on a Bridge — Programmers​

1. Problem Summary​

n trucks cross a bridge one by one.

Bridge constraints:

  • Length: bridge_length (each truck takes exactly this many seconds to cross)
  • Weight limit: weight

Rules:

  • Each truck moves 1 unit per second
  • A truck can only enter if total weight on bridge ≤ limit

Goal: Find the minimum time for all trucks to cross.

2. Approach​

Why this solution:

  • Time-based simulation — trucks enter and exit in order → Queue

Patterns applied:

  • Queue / Simulation
  • Fixed-size Sliding Window (bridge_length)

Theory connection:

  • Queue: truck enters → enqueue, truck exits → dequeue
  • Bridge = a "fixed-length window"
  • Optimization: avoid sum() on every step to prevent O(n²)

3. Solution Idea​

Model:

  • Queue bridge of size = bridge_length
  • Each slot = truck weight (or 0 if empty)

Process (each second):

1. Pop front of bridge → truck exits
   → decrease current_weight

2. Check next truck:
   - If fits → push truck weight
   - If doesn't fit → push 0

3. Increment time

💡 Key Insight: "The bridge IS a fixed-size queue."

4. Code​

from collections import deque

def solution(bridge_length, weight, truck_weights):
    bridge = deque([0] * bridge_length)
    truck_weights = deque(truck_weights)

    time = 0
    current_weight = 0

    while bridge:
        time += 1

        # truck exits the bridge
        current_weight -= bridge.popleft()

        if truck_weights:
            if current_weight + truck_weights[0] <= weight:
                truck = truck_weights.popleft()
                bridge.append(truck)
                current_weight += truck
            else:
                bridge.append(0)

    return time

5. Complexity​

TypeComplexity
TimeO(n)
SpaceO(bridge_length)

6. Key Learnings​

1. Recognizing the pattern

Simulation + Queue: "movement over time" → think Queue immediately

2. Critical trick

  • ❌ Don't use sum(bridge) → TLE: O(n²)
  • ✅ Track current_weight as a running variable

3. Key insight

No need to track detailed positions — just need: fixed-length queue + current weight

4. DSA Mapping:

Real WorldDSA
BridgeQueue
Truck entersenqueue
Truck exitsdequeue
Timeloop iteration

5. Level-up:

Queue can simulate time-based systems, not just process lists.

Problem 3: Sliding Window Maximum — LeetCode​

1. Problem Summary​

Given array nums and integer k. A window of size k slides from left to right.

Goal: For each window position, return the maximum value.

Output: Array of maximums for each window.

2. Approach​

Why this solution:

  • Brute force: scan k elements per window → O(n·k) → TLE
  • Need to optimize to O(n) → use Monotonic Deque

Patterns applied:

  • Fixed-size Sliding Window
  • Monotonic Deque (decreasing)
  • Greedy (discard useless elements)

Theory connection:

  • Deque maintains decreasing order
  • Front is always the current max
  • When a new element arrives: remove all smaller elements from the back — they can "never be the max again"

3. Solution Idea​

Data structure: Deque storing indices, maintaining:

nums[dq[0]] >= nums[dq[1]] >= ...

Algorithm:

dq = deque()
result = []

for i in range(len(nums)):
    # Step 1: Remove out-of-window elements from front
    if dq and dq[0] < i - k + 1:
        dq.popleft()

    # Step 2: Maintain decreasing deque — remove weaker elements
    while dq and nums[dq[-1]] < nums[i]:
        dq.pop()

    # Step 3: Add current index
    dq.append(i)

    # Step 4: Record result once first window is complete
    if i >= k - 1:
        result.append(nums[dq[0]])

💡 Key Insight: Each element enters the deque once and exits once → O(n) total.

4. Code​

from collections import deque

class Solution:
    def maxSlidingWindow(self, nums, k):
        dq = deque()
        result = []

        for i in range(len(nums)):
            # remove out-of-window elements from front
            if dq and dq[0] < i - k + 1:
                dq.popleft()

            # maintain decreasing deque
            while dq and nums[dq[-1]] < nums[i]:
                dq.pop()

            dq.append(i)

            if i >= k - 1:
                result.append(nums[dq[0]])

        return result

5. Complexity​

TypeComplexity
TimeO(n)
SpaceO(n)

6. Key Learnings​

1. Recognizing the classic pattern

"max/min of subarray of size k" → think Monotonic Deque immediately

2. Most important insight

Don't keep all elements — only keep "candidates that could be the max"

3. Greedy elimination thinking

Elements smaller than the new one → useless forever → remove immediately

4. Common mistakes:

  • Using max() each time → O(n·k)
  • Using Priority Queue but forgetting to expire old elements
  • Storing values instead of indices

5. DSA Mapping:

ComponentMeaning
WindowCurrent subarray
DequeStores candidates
FrontCurrent maximum
Pop backEliminate weaker element

6. Level-up:

"Monotonic Queue = the weapon for optimizing Sliding Window problems"

Problem 4: Feature Development — Programmers​

1. Problem Summary​

Tasks are developed in order. Each task has:

  • progresses[i]: current completion percentage
  • speeds[i]: daily progress rate

Rules:

  • A task can only be deployed when it reaches 100%
  • A task behind must wait for the task in front, even if it finishes earlier
  • When deploying → consecutive ready tasks are deployed together

Goal: Return the number of tasks deployed in each batch.

2. Approach​

Why this solution:

  • Tasks must be processed in order
  • Front task determines when back tasks deploy → Queue / Sequential Processing

Patterns applied:

  • Queue
  • Greedy + Grouping
  • Prefix grouping (group consecutive elements)

Theory connection:

Two thinking approaches:

  1. Simulation — increment progress each day, check front
  2. Optimization (better) — precompute completion days, then group

3. Solution Idea​

Step 1: Calculate completion days

days[i] = ceil((100 - progresses[i]) / speeds[i])

Step 2: Group deploy batches

# Key logic:
# First task → sets current_max_day
# For each subsequent task:
#   if day <= current_max_day → same batch
#   if day > current_max_day → new batch starts

result = []
current_max = days[0]
count = 1

for i in range(1, len(days)):
    if days[i] <= current_max:
        count += 1
    else:
        result.append(count)
        current_max = days[i]
        count = 1

result.append(count)

💡 Insight: We don't care about tasks finishing early — only the first task in each group determines the batch's deploy day.

4. Code​

import math

def solution(progresses, speeds):
    answer = []

    # Step 1: calculate completion days
    days = [math.ceil((100 - p) / s) for p, s in zip(progresses, speeds)]

    # Step 2: group deploy batches
    current_max = days[0]
    count = 1

    for i in range(1, len(days)):
        if days[i] <= current_max:
            count += 1
        else:
            answer.append(count)
            current_max = days[i]
            count = 1

    answer.append(count)

    return answer

5. Complexity​

TypeComplexity
TimeO(n)
SpaceO(n)

6. Key Learnings​

1. Recognizing the critical pattern

"must follow order", "wait for the one before" → Queue mindset

2. Thinking optimization

  • ❌ Wrong: simulate day by day
  • ✅ Correct: math modeling → compute directly

3. Hardest insight of this problem

Output is not one entry per task — it's grouped batches

4. Powerful trick

Use current_max to group batches — no actual queue structure needed

5. DSA Mapping:

Real WorldDSA
Tasks waiting on each otherQueue
Completion dayPreprocessing
Deploy in batchesGreedy grouping

6. Level-up:

Queue doesn't always require an actual queue structure — it can "transform" into array + logic for efficiency.
