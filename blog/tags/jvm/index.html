Understanding the Java Platform – Execution Flow & JVM Architecture

November 2, 2026 · 5 min read
Mai Duc Anh
Blogger & Developer

1. Java Platform Overview​

Java is not merely a programming language — it is a complete platform (the Java Platform).

👉 When we talk about "programming in Java", we are actually working with 3 core components:

  • Java Language
  • JVM (Java Virtual Machine)
  • Library and tooling ecosystem

Core Design Goal of Java​

Write Once, Run Anywhere (WORA)

Write your code once, and run it on:

  • Windows
  • Linux
  • macOS

… without modifying the code.

2. The Role of JDK, JRE, and JVM​

These three concepts are a common source of confusion for Java learners — so let's clarify them definitively.

2.1 JVM – Java Virtual Machine​

What is the JVM?

  • The JVM is a virtual machine
  • It executes Java bytecode
  • It acts as an intermediary layer between Java and the operating system

📌 The JVM:

  • Does not understand .java files
  • Does not understand .exe files
  • Only understands .class files (bytecode)

👉 Each operating system has its own JVM implementation, but:

  • The bytecode itself is identical across all platforms

2.2 JRE – Java Runtime Environment​

The JRE consists of:

  • JVM
  • Core Java Libraries (java.lang, java.util, ...)
  • Runtime configuration files

👉 The JRE is used to:

  • Run Java programs
  • ❌ Not for writing or compiling code

📌 With only the JRE installed:

  • You can run .class files
  • ❌ You cannot compile .java files

2.3 JDK – Java Development Kit​

JDK = JRE + Development Tools

Includes:

  • javac (compiler)
  • java (launcher)
  • javadoc, jdb, ...

👉 The JDK is used for:

  • Writing code
  • Compiling
  • Running
  • Debugging

📌 When installing Java for development purposes: ➡️ Always install the JDK

2.4 Overall Relationship​

JDK
├── JRE
│ ├── JVM
│ └── Java Core Libraries
└── Development Tools

3. Relationship Between Java Language and the Java Platform​

Java Language​

  • Syntax and keywords
  • Data types
  • OOP concepts (classes, objects, inheritance)
  • Source files with .java extension

Java Platform​

  • JVM (Java Virtual Machine)
  • ClassLoader Subsystem
  • Runtime Data Areas
  • Execution Engine & Garbage Collector

The Java Language is only the visible surface.
The Java Platform is what ultimately determines how a program executes.

4. Java Execution Flow​

When you run a Java program, the JVM does not execute the .java file directly.

General Execution Flow​

IDE
↓ (Save)
Hello.java (Disk)
↓ (Compile)
javac Hello.java
↓
Hello.class (Bytecode)
↓
JVM (RAM)
↓
OS
↓
CPU execution

5. Compile-time and Runtime in Java​

5.1 Compile-time​

Triggered when running:

javac Hello.java

Input:

  • .java file (source code)

What Java does:

  • Validates syntax
  • Performs type checking
  • Compiles to bytecode

Output:

  • .class file

📌 Compile-time does not execute the program.

5.2 Runtime​

Triggered when running:

java Hello

Input:

  • .class file

What Java does:

  • JVM loads the class
  • Verifies bytecode
  • Executes the program

📌 Runtime is when the program actually runs.

6. What is Bytecode? Why is Java Portable?​

What is Bytecode?

  • An intermediate representation
  • Not native machine code
  • Platform and CPU-independent

📌 Bytecode:

  • Runs on the JVM
  • The JVM translates it further into native machine code

Why does Java run across multiple platforms?

Java Source (.java)
↓
Bytecode (.class)
↓
┌─────────────┐
│ JVM Windows │ → CPU Windows
│ JVM Linux │ → CPU Linux
│ JVM macOS │ → CPU macOS
└─────────────┘

👉 Java does not run directly on the OS.
👉 The JVM is what runs on the OS.

7. JVM Architecture​

The JVM consists of 3 major subsystems:

  • ClassLoader Subsystem
  • Runtime Data Areas
  • Execution Engine

8. ClassLoader Subsystem​

Responsibilities:

  • Load .class files into the JVM
  • Verify their validity
  • Prepare classes for execution

ClassLoader Types in the JVM​

  • Bootstrap ClassLoader
    Loads Java's core classes (e.g., java.lang, java.util)

  • Platform ClassLoader (Java 9+)
    Loads Java Platform libraries (e.g., java.sql, java.xml)

  • Application ClassLoader
    Loads classes written by the developer (from the classpath)

📌 Classes are loaded only when required (lazy loading).

9. Runtime Data Areas – JVM Memory Regions​

9.1 Method Area​

Stores:

  • Class metadata
  • Method information
  • Static variables

9.2 Heap​

  • Stores objects
  • Shared across the entire JVM
  • Managed by the Garbage Collector

9.3 Stack​

Each thread has its own dedicated Stack.

Stores:

  • Local variables
  • Method call information
  • References

📌 Stack: small and fast
📌 Heap: larger and relatively slower

9.4 PC Register​

Stores the address of the currently executing bytecode instruction.

9.5 Native Method Stack​

Used for native code written in C/C++.

10. Execution Engine​

10.1 Interpreter​

  • Reads bytecode
  • Executes each instruction sequentially

📌 Advantage:

  • Starts execution immediately

📌 Disadvantage:

  • Slow for code that is executed repeatedly

10.2 JIT Compiler (Just-In-Time)​

What the JIT does:

  • Detects frequently executed code paths (hot spots)
  • Compiles bytecode → native machine code
  • Caches the result for reuse

📌 Modern JVMs use:

  • Interpreter + JIT
  • The JVM self-optimizes as the program runs

11. Summary​

Detailed slide reference:

  • 🔗 https://www.canva.com/design/DAHApyPYZmw/AQAchpZL_3B77rpOe4-3YQ/edit

Java is not simply a language — it is a complete platform comprising the JDK, JRE, and JVM. A Java program does not run directly on the operating system; it must first be compiled into bytecode, which is then interpreted and optimized by the JIT compiler inside the JVM before the CPU executes it.

A solid understanding of:

  • The Java Platform
  • The Execution Flow
  • JVM Architecture

enables developers to:

  • Gain deep insight into how Java works under the hood
  • Debug more effectively
  • Write more optimized code
  • Build a strong foundation for learning Spring, JVM tuning, and advanced backend development

Analyzing the JVM Execution Mechanism Through a Concrete Code Example

February 22, 2026 · 10 min read
Mai Duc Anh
Blogger & Developer

In this post, we will analyze the complete JVM execution mechanism when running the following code:

class Student {
    int age;
}

public class Main {
    public static void main(String[] args) {
        Student s1 = new Student();
        s1.age = 20;

        Student s2 = s1;
        s2.age = 25;

        int x = 10;
        int y = x;

        System.out.println("s1.age = " + s1.age);
        System.out.println("s2.age = " + s2.age);
        System.out.println("x = " + x);
        System.out.println("y = " + y);
    }
}

I. INPUT AND OUTPUT OF THE JVM​

INPUT
When running:

java Main

The JVM receives as input:

  • Main.class — the compiled output of Main.java

  • Student.class — the compiled output of Student.java

  • The bytecode (an intermediate representation produced after compiling .java files, which is then executed by the JVM) contained within these files

⚠️ Note: The JVM (the virtual machine that executes Java programs) does not run .java source code — it runs the bytecode inside .class files.

OUTPUT

  • Console output (the result printed to the screen)

  • Memory state changes
  • Objects (instances created from a class) allocated in the Heap (the JVM memory region used to store objects)
  • Stack Frames (a block of data created each time a method is invoked; it resides in the Java Stack of each thread) being pushed and popped

Console output:

s1.age = 25
s2.age = 25
x = 10
y = 10

II. CLASS LOADER SUBSYSTEM (The JVM component responsible for loading .class files into memory and preparing them for execution)​

1. Loading (The process of reading .class files and bringing them into JVM memory)

The Application ClassLoader loads:

  • Main.class
  • Student.class
  • Class metadata is stored in the Method Area

The Method Area is a memory region used to store information about loaded classes, including:

  • Method bytecode
  • Class metadata
  • Runtime Constant Pool
  • Static variables

Metadata is data that describes a class, including:

  • Class name: Student
  • Superclass: Object
  • List of fields
  • List of methods
  • Access modifiers

2. Linking (A safety verification step)

Consists of 3 sub-steps:

✔ Verify (Checks whether the bytecode is valid and safe)

  • Validates bytecode correctness
  • Ensures no stack overflow
  • Ensures no incorrect type access

✔ Prepare (Allocates memory for static variables and assigns default values)

  • Allocates memory for static fields (if any)
  • Assigns default values

✔ Resolve (Converts symbolic references into direct references)

  • Transforms symbolic references → direct references
  • A symbolic reference is textual information (e.g., a class or method name as a string)
  • A direct reference is the actual memory address of the method at runtime

3. Initialization

  • Executes static blocks (a block of code that runs exactly once when the class is first loaded) if present
  • Initializes static variables (which reside in the Method Area)

After this phase, the Method Area contains:

Class Student
  field: age
  constructor

Class Main
  method: main()
  bytecode
  constant pool

What is the Constant Pool?

  • The Constant Pool is a table containing all "constants" and "symbolic references" used by the class.
  • It resides inside the .class file.

A constructor is a special method of a class, used to initialize an object when it is created with the new keyword.

III. 16-STEP RUNTIME WALKTHROUGH VIA JAVA VISUALIZER​

STEP 1 — JVM initializes the process (a program currently running in the operating system)

Why does it show main:7?

  • The JVM has no concept of "line 7"
  • The JVM only understands bytecode indices
  • main:7 is displayed by the Java Visualizer, which maps bytecode indices back to corresponding source lines

The PC Register (a small memory region that stores the address of the bytecode instruction currently being executed by the thread) points to the first bytecode instruction of the main method. The tool displays this as main:7 because that is the corresponding source line.

The operating system creates a new PROCESS.

This process contains:

  • Heap (memory region for storing objects and class instances)
  • Method Area (stores class information after loading)
  • Stack (a thread component that stores local variables, references to objects, the operand stack, and method call information)
  • PC Register (a small memory region storing the address of the bytecode instruction currently being executed)
  • Native Method Stack (used when Java calls native methods written in C/C++)

These collectively form the JVM Runtime Data Areas.

The ClassLoader begins operating.

The JVM does not immediately run main. It must first:

  • Load class Main
  • Load class Student

Mechanism: The Application ClassLoader will:

  • Read Main.class
  • Load its bytecode into the Method Area

STEP 2 — Create the Main Thread

The JVM creates:

  • Main Thread (the first thread created when a Java program starts)
  • Stack (each thread has its own dedicated Stack; the JVM creates a Stack Frame)
  • Frame main (the Stack Frame created when main() is invoked)

When the Main Thread is created, the JVM allocates a dedicated Stack for it and pushes a stack frame for main() onto the Stack. This frame contains an empty local variable array and an empty operand stack. The PC Register is set to point to the first bytecode instruction of main (the Visualizer displays this as the corresponding source line number, but the JVM internally only tracks the bytecode index).

The operand stack is a memory region inside each Stack Frame used to store operands and intermediate results during bytecode execution.

STEP 3 — new Student()

The JVM encounters new Student():

  • Allocates a new object in the Heap
  • The field age is assigned the default value 0

Stack at this point:

  • Still only contains frame main()

<init> is the special bytecode name for constructors. Inside the <init> frame, the first local variable is always this. this is a reference to the object currently being initialized.

When executing Student s1 = new Student(), the JVM sees the bytecode instruction to create a new object — it allocates memory in the Heap for a Student with a default age of 0, then pushes a reference to this object onto the operand stack of frame main().

STEP 4 — Invoke the constructor

The JVM invokes the <init> constructor by creating a new stack frame for <init> and pushing it onto the Stack. The <init> frame contains a first local variable this, which is a reference pointing to the newly created object in the Heap — this tells the constructor which object is being initialized.

STEP 5 — Constructor returns

Once the constructor completes, the <init> frame is popped off the Stack, returning control to frame main.

STEP 6 — Assign to s1

Inside frame main(), the JVM takes the reference returned by the constructor and stores it in the local variable slot for s1. At this point, frame main() in the Stack contains an entry s1 holding a reference that points to a Student object in the Heap, where age = 0.

STEP 7 — s1.age = 20

What the JVM does:

  • Retrieves the reference s1 from the Stack
  • Follows the address into the Heap
  • Locates the field age
  • Updates the value to 20

When the JVM sees s1.age = 20, it retrieves the reference from s1 in the Stack, follows the address into the Heap, finds the age field of the object, and sets it to 20. The Heap now contains a Student object with age = 20.

STEP 8 — Student s2 = s1

The JVM does NOT create a new object.

It only:

  • Copies the reference value from s1
  • Assigns it to s2

Student s2 = s1 does not allocate a new object — it simply copies the reference value from s1 to s2 inside frame main(). As a result, both s1 and s2 in the Stack point to the same object in the Heap.

=> s1 and s2 reference the same object.

STEP 9 — s2.age = 25

The JVM:

  • Retrieves the reference from s2
  • Follows it to the object in the Heap
  • Updates age = 25

When executing s2.age = 25, the JVM accesses the object in the Heap via the reference stored in s2 and updates the age field to 25. Since both references point to the same object, both s1.age and s2.age now reflect the value 25.

STEP 10 — int x = 10

When the JVM encounters int x = 10, it stores the integer value 10 directly into a slot in the local variable array of frame main().

The Heap is unchanged.

STEP 11 — int y = x

int y = x copies the value 10 from x to y. Both x and y are now separate integer variables in the Stack, each holding the value 10, with no involvement of the Heap.

No references are involved here.

STEP 12 — Preparing the first println

What the JVM does:

  • Retrieves data from the Stack or Heap
  • Pushes it onto the operand stack
  • Invokes println()

When processing System.out.println calls, the JVM sequentially retrieves the required values from the Stack or accesses fields in the Heap via references, pushes them onto the operand stack, and invokes the println() methods.

STEP 13 — Invoke println()

Same process as Step 12.

STEP 14 — Print x

Same process as Step 12.

STEP 15 — Print y

Same process as Step 12.

STEP 16 — main() completes

Stack state during println calls:

Frame println()
Frame main()

After each print completes:

  • Frame println() is popped.

The JVM creates temporary stack frames for each method call and pops them after execution completes.

The Stack is now empty.

The object in the Heap has no remaining references.

  • The Garbage Collector will reclaim it in a future collection cycle.

Finally, when main() completes, the JVM pops frame main() off the Stack, leaving the Stack empty. The Student object in the Heap now has no references pointing to it and is therefore eligible for garbage collection. The Heap retains the object until the GC runs and reclaims it.

V. Conclusion​

Detailed slide reference:

  • 🔗 https://www.canva.com/design/DAHBYC9gqew/Qj0cc0miT3og0gFKV8UZJw/edit

Core takeaways:

  • Objects always reside in the Heap
  • References reside in the Stack
  • Primitives reside in the Stack
  • A method call creates a new Stack Frame
  • The Constant Pool stores symbolic references
  • The Execution Engine reads and interprets bytecode
  • The GC reclaims objects when no references remain

Through this simple example, we can see that the JVM does not merely "run code" — it:

  • Loads classes
  • Verifies bytecode
  • Manages memory
  • Executes via a stack-based architecture
  • Invokes native code
  • Automatically performs garbage collection

A solid understanding of these mechanisms enables developers to:

  • Avoid memory leaks
  • Clearly distinguish references from primitives
  • Understand why and how GC operates
  • Debug JVM-related issues at a deeper level
